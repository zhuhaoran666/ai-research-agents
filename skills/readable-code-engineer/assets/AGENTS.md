# 代码维护约定

优先让维护者找到入口、理解主流程，并在明确位置安全修改业务规则。用户要求和本项目更具体的约定优先。

## 开发前

- 先读 README、相关实现、调用方和现有检查方式；检查并保留已有工作区改动。
- 确认本次输入、输出和兼容要求，沿当前项目语言与工具完成任务。
- 不为局部功能另建架构，不顺手更换工具链或整理无关文件。

## 实现

- 用业务含义清楚的命名和显式控制流；重要边界明确输入、输出、单位和失败行为。
- 职责清楚比固定行数重要；小程序允许多个清晰函数放在一个文件中。
- 新增抽象、依赖、配置和目录需要解决当前的具体问题。
- 同一业务规则保持明确维护位置；核心规则尽量与外部读写分开。
- 延续已有实现与决定；多轮修改后回看相关主流程，避免为同一能力累积并行路径或模式开关。
- 保留公开调用方式，包括可能用于关键字调用的形参名；整理代码不悄悄改变数值、随机性或性能约束。
- 只在能处理或补充上下文的边界捕获异常，不静默忽略失败。
- 注释解释原因和约束，不逐行复述代码；遵循项目已有文档语言。

## 完成前

- 运行与改动风险相称的已有检查；规则变更或有回归风险的整理应有针对性行为验证。
- 检查最终差异，移除无当前用途的新增设施，更新受本次影响的真实文档。
- 交接说明改了什么、实际验证结果，以及下一次类似修改应去哪个文件或函数。
- 未执行和失败的检查如实说明，不把预期结果写成已经通过。
