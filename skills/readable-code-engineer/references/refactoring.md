# 渐进整理难以理解的代码

适用于用户明确要求整理、简化或重构，或当前功能确实被局部复杂度阻碍时。让每一步的行为变化和结构变化可辨认，保持差异可审阅。

## 确定边界

1. 找到真实入口与调用方，读相关测试和说明，识别用户已有改动。不要先按文件名猜职责后重排目录。
2. 说明当前最费理解的具体问题及后果，例如“同一折扣规则在两个入口各维护一份”，而非只说“缺乏最佳实践”。
3. 明确保留的相关契约，包括公开调用方式、返回结构、异常类别、命令行输出和配置含义。公开形参名、配置键和序列化字段可能被代码库外部使用，不能仅凭本地搜索无引用就认定可改名。数值任务还要关注运算顺序、精度、随机状态、排序和资源约束；只展开本次受影响的部分。
4. 选择最小可交付范围。较大整理按调用链或业务能力分批，先完成当前批次；不要停在只写计划的状态。

## 建立行为依据

已有测试可覆盖目标路径时先运行相关测试。缺少证据但存在回归风险时，用代表性输入、边界和可定位的失败情况固定当前行为，再开始有风险的移动或拆分。基线已失败时保留失败与条件，后续区分既有问题和本次回归。

记录观察到的行为，不把旧行为自动认定为正确。发现疑似旧缺陷时，区分兼容整理与用户授权的修复；会改变关键结果且意图不明确时，提出这个具体疑问，同时继续不受影响的整理。

重构中的行为等价以本次相关的契约为准。不要为了让测试通过而改期望值、删用例或吞掉异常；测试本身错误时给出可核验依据，再修正。

## 优先考虑的局部变换

按实际问题选择，不要求每次全部使用：

- 将晦涩的内部变量和函数改为表达业务含义的名称，联动实际调用方。公开接口需要改善名称时，按真实兼容需求保留原调用方式或做范围明确的迁移；验证关键字调用等受影响用法，不为纯内部改名增加兼容包装。
- 用有含义的中间变量展开难懂的计算；保持运算顺序和精度约束。
- 用明确分支或提前返回降低嵌套，确认状态和资源清理语义未变。
- 把可独立理解的规则提为函数，把外部读写留在清楚边界；仍可保留在同一文件中。
- 合并语义相同、需要一起变化的重复规则；避免让不同规则共享大量模式开关。
- 对明确无用途的转发层和抽象做局部简化；删除前确认调用、动态注册和兼容用途。

一批改动围绕一个可描述的目标。分离全库格式调整、依赖升级和行为变更；若局部调整必须伴随功能修改，明确解释二者关系即可。

不要为了消除一次跳转把成熟模块全部塞回入口，也不要为缩短入口建立多层转发。判断依据是人能否顺着真实需求理解和修改。

## 核验并交接

- 对照改动前后的相关行为和现有调用方，运行适当验证。数值差异使用任务已有的容差或有依据的比较条件；不能为了通过检查临时放宽。涉及性能约束时使用可比输入和环境衡量受影响路径，不要求无关任务新增基准设施。
- 查看最终差异：是否遗漏引用、夹带无关格式改动、覆盖用户工作，或加入只服务于这次整理的临时包装。
- 注释和文档只保留长期有用的解释；记录新的修改入口，不保留一份已经过时的旧实现作为“参考”。
- 用具体收益报告结果，例如“校验规则集中到 `validate_record`，新增规则可在此修改”；不要只有“优化结构、提升质量”。
- 保留失败证据与尚未覆盖的边界，不声称有限测试证明了全部行为等价。
