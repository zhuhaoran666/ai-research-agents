# 建立轻量且可复现的开发环境

用于新项目、用户明确要求改善开发环境，或现有环境缺口阻碍当前任务时。目标是让维护者能启动、检查、定位和修改；项目大小决定需要多少设施。

## 从已有事实选择

检查依赖清单和锁文件、版本声明、项目脚本、持续集成、README、示例配置和忽略规则。以实际可运行的命令为准，记录文档与现状的差异。

- 已有管理器与锁文件时沿用，避免引入第二个管理器或无关升级。依赖必须改变时只更新相关范围，并核对清单与锁文件一致。
- 多种工具并存时，先找项目文档和持续集成使用的主路径，不擅自大面积清理历史工具。
- 没有现成环境时，先选一个与任务匹配的主语言和最小运行路径。小型标准库工具可以没有外部依赖；Web、数据库或数值任务可使用减少维护工作的成熟库，不为了“零依赖”重造复杂组件。
- 工具参数或版本不确定时，查看本地帮助或核对官方资料。不要生成未经核对的“最新版本”声明。

## 按实际需要落地

| 维护者的问题 | 应提供的最小支持 | 避免的负担 |
| --- | --- | --- |
| 从哪里开始看？ | 明确的执行入口，README 中一条真实主流程 | 为整齐建立许多空目录或空层 |
| 怎样第一次运行？ | 运行前提、必要安装、完整启动命令和小样例 | 只写“运行项目”，遗漏工作目录或必需配置 |
| 怎样知道没改坏？ | 已有检查命令；多项检查才需要统一入口 | 给单文件工具引入庞大的任务系统 |
| 配置在哪里？ | 必需配置的名称、用途和安全示例 | 为每个常量新增环境变量 |
| 要修改功能去哪里？ | 两三个与实际需求相关的“修改点 → 文件/函数” | 生成逐文件复述代码的文档 |

### 代码与目录

把最常变化的业务逻辑放在名称明确的位置；入口负责组织步骤。开始可以只有一个源文件，出现不同变化原因或边界后再拆分。中型项目沿业务能力组织，边界内再区分输入输出与规则；既有框架遵循其习惯。

配置和常量优先靠近用途；多处共享且语义一致时再集中。缓存、日志、构建产物和临时数据与源代码区分；依据项目实际产物完善忽略规则，不隐去应受版本控制的源码、迁移或夹具。

### 一条运行路径和一条检查路径

- 优先使用现有项目脚本、构建系统或任务入口；没有时，简单的直接命令也可以。
- 运行命令说明工作目录、必需参数和最小输入。需要凭据或外部服务时，清楚标明必要条件；能用本地样例验证的部分先验证。
- 统一检查只组合有用的检查，并保证任一子步骤失败会使总命令失败。格式检查和自动修改格式的命令清楚区分。
- 自动格式化只覆盖本次范围；避免与行为变更混入全库格式差异。大范围格式统一应作为用户要求的独立工作。
- 类型检查、测试、静态检查按风险与语言选择；已有工具足够就复用。没有外部检查器的小脚本，可用针对性运行与标准库测试建立反馈，不为凑齐工具安装整套设施。
- 无法完整运行时报告具体缺项，同时执行可完成的验证；不伪造检查结果，不顺手启动付费或生产服务来追求全绿。

### 最少的维护文档

README 只写实际存在的内容：用途、首次运行、检查方法、入口与数据流、常见修改位置。命令必须可复制且与当前代码一致；不要留下“以后补充”的模板章节。

只有在维护者难以从这些内容理解系统时，才新增简短架构说明，记录模块职责、数据或状态归属和关键取舍。值得长期保留的取舍写明“为什么当前这样做”与适用条件，不为每次提交新建决策文档。

需要代理约定时，从 [../assets/AGENTS.md](../assets/AGENTS.md) 挑选适合的内容，再填入项目已核实的入口与命令。已有 AGENTS.md 应保留并局部合并，遵循其适用范围。不要修改用户级设置、其他项目或全局 Git/编辑器配置。

## 退出标准

维护者按 README 能进入项目并找到主流程；必要命令有实际执行证据或明确的未执行原因；常见修改位置可定位；本次新增设施的用途可解释。不要以文件数量、工具数量或覆盖率代替这些结果。
